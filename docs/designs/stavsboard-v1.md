## Problem Statement

Glances shows everything about a machine, but it is dense and cluttered. Stavsboard is a
self-hosted, single-machine system monitor with a web dashboard that shows the core data
calmly, so the owner can read machine state at a glance. It runs on Windows 11 and Linux and
is read-only: it never kills processes or changes system state.

Primary user: the builder. Two viewing contexts:
1. A browser tab on a Windows machine that "will almost never be full sized on the screen".
2. A phone or laptop checking "from afar" on the home LAN.

## What Makes This Cool

- A quiet screen means a healthy machine. Color appears only when something is off.
- The answer to "is anything wrong, and did anything happen while I was away?" is readable in
  one second on a phone.
- The same core data as Glances, at a fraction of the visual noise.

## Constraints

- Runs on Windows 11 and Linux. One documented command starts it.
- Binds to `127.0.0.1` by default. LAN exposure only via an explicit opt-in flag.
- Read-only. No process control, no writes to system state, no elevated/admin rights.
- No auth, multi-host, persistent history (disk), or external alerting in v1.
- Glances is a reference for which metrics matter only. No code, layout or branding copied.
- Refresh at least every 2s without visible jank. Works at 375px and 1440px, light and dark.

## Premises (agreed)

1. **Access:** default bind `127.0.0.1`; `--lan` flag binds `0.0.0.0` for phone/laptop access.
   The README warns that there is no auth, so anyone on the LAN can see the process list while
   `--lan` is on.
2. **Sensors:** temps and fans via psutil on Linux. On Windows every known method needs admin
   (psutil has no Windows sensor support; WMI and LibreHardwareMonitor need elevation), so the
   card shows a quiet "not available on this system" state. Nothing runs elevated.
3. **Containers:** Docker only, via the official `docker` Python SDK over the local
   socket/named pipe, read-only (name, state, CPU %, memory). The card hides itself when Docker
   is not reachable.
4. **Metrics in v1:** CPU (total + per-core), memory + swap, top ~10 processes by CPU/RAM
   (read-only), sensors (Linux), Docker containers.
   **Cut from v1:** disk I/O, network, load average, filesystems, history on disk, auth,
   multi-host, external notifications.
5. **"Simple and nice to look at" means:**
   - Few, big numbers: one headline value per card. Detail is secondary.
   - Color = alarm only: neutral when healthy, amber/red only when a threshold is crossed.
   - Narrow-first layout: designed for 375px and a half-width tab first, then scaled up.
   - Short sparklines (~60s, in memory) live only in a separate **Trends** tab, hidden unless
     needed.
6. **Warnings (in-dashboard only):** fixed thresholds (e.g. CPU > 90% sustained 10s, RAM > 90%,
   heavy swap, high temperature, container exited). On a crossing, the card turns amber/red, a
   calm banner names the problem, and the tab title gets a marker (`● Stavsboard`). No browser
   notifications, no config file in v1. The exact thresholds get locked in eng review.
7. **Warning log (revised after second opinion):** the server keeps a short in-memory log of
   recent threshold crossings, with start, end, peak and duration (e.g. "RAM hit 92% at 03:14
   for 4 min"). It resets on restart and is never written to disk. This answers "did anything
   happen while I was away?". Trends stay at ~60s.

## Approaches Considered

- **A) Stdlib + polling:** `http.server` + psutil + docker SDK, browser polls JSON every 2s.
  Fewest dependencies, but more hand-rolled HTTP code. Not chosen.
- **C) Glances REST API as backend:** fastest to data, but it breaks the "reference only" rule
  and makes "one command" heavy. Rejected.

## Recommended Approach (chosen): B) FastAPI + SSE

- **Backend:** Python 3.11+, FastAPI + uvicorn, psutil, docker SDK.
  - A collector thread samples every ~1s into a single snapshot. Per-process CPU uses cached
    `psutil.Process` objects so values are correct from the second tick.
  - A threshold module (pure functions: snapshot + previous state → warnings) feeds the
    warning log. This is the main unit-test target.
  - Endpoints: `GET /api/snapshot` (JSON), `GET /api/stream` (SSE push), static files.
  - CLI: `--port`, `--lan`. Default host `127.0.0.1`.
- **Frontend:** vanilla HTML/CSS/JS with no build step, served by the same process. Two tabs:
  **Now** (cards + banner + warning log) and **Trends** (60s sparklines, client-side ring
  buffer). Light and dark themes via CSS custom properties and `prefers-color-scheme`.
- **Why:** SSE gives jank-free push under 2s and the modules are testable. It needs two more
  dependencies than Approach A (FastAPI, uvicorn).

## Committed Behavior (from spec review)

- **Stale/disconnected data is never calm.** The client tracks the time of the last update. If
  no update arrives for more than 5s, it shows a distinct "Disconnected, data Ns old" state
  that counts as non-calm (not colorless), and the tab-title marker changes. `EventSource`
  retries automatically. On reconnect the client resyncs from `GET /api/snapshot`, which
  includes active warnings and the warning log.
- **Containers on their own poller.** Docker collection runs in a separate thread on a slower
  cadence (~3-5s), fully decoupled from the 1s psutil collector, so a slow or hung daemon can't
  stall CPU, memory or process data. Container CPU % is computed from consecutive stats
  samples, with a per-call timeout. Exact cadence and timeout get locked in eng review.
  Container data carries its own `updated_at` timestamp. If it is older than 3x the poller
  cadence (daemon slow, hung or timing out), the Containers card shows a quiet "Container data
  Ns old" stale state, counted as non-calm, instead of the last values, even while the rest of
  the stream is live. Container data age is measured on the server clock only: the server sends
  `container_age_s` and a `containers_stale` flag in each pushed snapshot, and the client never
  compares timestamps with the viewer device's clock.
- **Process access is honest without admin.** `AccessDenied` fields are shown as unavailable
  rather than crashing or dropping the row. Processes that still report CPU/RSS stay eligible
  for top 10. Cached `psutil.Process` objects are evicted on `NoSuchProcess` and on PID reuse
  (`create_time` mismatch).
- **Exposed process fields:** name, PID, CPU %, memory (RSS) only. No command line, environment,
  username or open files, in the UI, the SSE payload or the JSON API.
- **DNS-rebinding protection:** a Host header allowlist (`localhost`, `127.0.0.1`, `[::1]`, plus
  the machine's LAN IP/hostname only when `--lan` is set). No permissive CORS.
- **LAN firewall:** Stavsboard never changes firewall settings. The README documents that with
  `--lan` on Windows the user must accept the Defender Firewall prompt or add an inbound rule
  themselves, and notes the equivalent for Linux host firewalls (ufw/firewalld).
- **Docker access:** on Windows the docker SDK uses the Docker Desktop named pipe via `pywin32`.
  This is a Windows-only transitive dependency of the docker SDK; eng review verifies it gets
  installed. Access depends on the user's existing `docker-users`/`docker` group membership,
  and Stavsboard never elevates. If Docker isn't running, the card hides. If access is denied,
  the card shows a quiet "No access to Docker" state.
- **Warning latency:** measured from the moment the threshold module raises a warning (after
  any sustain window) to on-screen render. Target: within one collector tick plus push (≤ 2s).

## Reviewer Concerns

### R3-1 — feasibility (blocking)

**Problem**

> The new stale check does not say which clock measures the age of `updated_at`. The server sets the timestamp, but the viewer is often a phone or laptop on the LAN. If the browser compares it with its own clock, normal clock skew between devices breaks the check in both directions. A viewer clock that runs behind keeps stale container data looking calm, which breaks 'Stale data is never shown as calm.' A viewer clock that runs ahead shows a false non-calm stale state on a healthy machine, which breaks 'Healthy machine = no color on screen.'

**Remedy**

> Measure container data age on the server's clock only. Either have the server send `container_age_s` with each pushed snapshot and decide the stale flag itself, or have the client compare `updated_at` with the server's own snapshot timestamp in the same payload, never with the device clock. State which one the design uses.

### R3-2 — completeness (minor)

**Problem**

> Part of the R2-1 remedy is still unaddressed. Each poll makes several Docker calls (a list call, then a stats call per container), and each call has its own timeout. The design does not say whether one container's timed-out stats call advances `updated_at` (with that container's CPU % marked unavailable) or leaves the whole card's timestamp unchanged. So it is unclear whether one slow container makes the whole card stale or only blanks its own CPU %.

**Remedy**

> Say that `updated_at` advances only when the container list call succeeds, and that a timed-out per-container stats call shows only that container's CPU % as unavailable. Or state the opposite rule if that is the intent.

### R3-3 — completeness (minor)

**Problem**

> The Containers card's state from server start until the first successful container poll is undefined. `updated_at` has no value yet, and the 3x cadence rule does not say whether the card shows loading, hides, or appears stale.

**Remedy**

> State the startup state, for example a quiet 'loading' state that is not counted as non-calm until 3x cadence has passed since server start.

### R3-4 — feasibility (minor)

**Problem**

> Persisting from R2-2: the --lan Host allowlist is still described as 'the machine's LAN IP/hostname'. This can reject legitimate access through another interface address, a DHCP address that changed, or hostname.local.

**Remedy**

> State how the --lan allowlist is built (all interface addresses plus hostname and hostname.local, checked against current addresses) and document the rejection behavior in the README.

### R3-5 — clarity (minor)

**Problem**

> Persisting from R2-3: the disconnected state's tab-title marker 'changes', but its new form is still not given, so a background-tab viewer may not be able to tell a disconnect from a warning.

**Remedy**

> Name the disconnected title form (e.g. '○ Stavsboard (disconnected)'), distinct from '● Stavsboard'.

### R3-6 — clarity (minor)

**Problem**

> Persisting from R2-4: Premise 6 still lists 'container exited' as a warning without defining the trigger. Intentionally stopped containers, one-shot containers that exit 0, and containers already exited at startup are not handled.

**Remedy**

> Define the trigger (e.g. a running container moves to exited with a non-zero code, or a restart loop) and say whether containers already exited at startup warn.

### R3-7 — clarity (minor)

**Problem**

> Persisting from R2-5: the SSE payload shape (full snapshot or deltas, whether it carries warnings, the log and container `updated_at`) and its push cadence relative to the 1s collector and the 3-5s container poller are still unstated.

**Remedy**

> State the SSE payload shape and push cadence, and how the slower poller's container data and its timestamp are merged into pushed snapshots.

### R3-8 — completeness (minor)

**Problem**

> Persisting from R2-6: Trends still use a client-side ring buffer, so sparklines start empty and reset on every reconnect or reload.

**Remedy**

> Either accept this and give Trends an empty-state message, or have the server keep 60s of history in memory and include it in /api/snapshot.

### R3-9 — completeness (minor)

**Problem**

> Persisting from R2-7: per-core CPU display at 375px is still unaddressed for machines with 16-32+ logical cores.

**Remedy**

> Note that per-core detail is secondary (collapsed, a compact strip, or Trends-only) and must fit 375px at high core counts.

### R3-10 — completeness (minor)

**Problem**

> Persisting from R2-8: warning log entries that are still active have no end or duration representation, and timestamp timezone handling across devices is undefined.

**Remedy**

> State that active entries show 'ongoing since HH:MM' and that timestamps are sent as UTC/epoch and rendered in the viewer's local time.
